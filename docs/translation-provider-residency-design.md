# Translation model residency: integration requirements

13 October 2026. This historical feasibility design informed the implemented [production integration](translation-production-integration.md). The implementation adds the user's subsequent requirement: retention between captures is optional and defaults off; models remain loaded throughout one capture's review. The discussion below describes the earlier design and prototype evidence. Best-effort model selection no longer requires bilingual review, another PC, or a fixed 2× time limit.

The application currently creates a new `ServiceJob` through `TaskPool.start()` in `src/language_lens/services/jobs.py`. `ProcessJob._start()` launches a process and closes its input after one request. `task_worker.execute()` constructs an `ArgosTranslator`; `main()` exits when that request finishes. Captures and expanded searches therefore cannot rely on session-long model retention. Keeping a Python wrapper in the review window does not retain the subprocess's model weights.

A replacement should use an application-owned translation process with a bounded request protocol. Preparation loads the chosen route once. Full selected text, compact isolated-word lookups and expanded isolated-word lookups use that same resident service. Each request carries a request ID, capture generation, language pair and function. Results retain the existing sentence/word candidate structure. The engines receive the same selected text or isolated word as today; no context-based word flow is introduced.

Pin the active pair's required backends for the application session. An explicit language change prepares a different pair; screenshots and expanded requests do not trigger model loading. One multilingual SMaLL-100 backend can serve its registered language labels using the verified target-prefix contract. For a native full-text provider, retain Argos for both word functions. A hybrid native Turkish→English plus Argos English→target route should share Argos package backends with the word route rather than duplicate the pivot in separate production processes. The benchmark prototype keeps those workers separate and reports their combined RAM; that is a conservative prototype cost, not an optimized production memory claim.

Use a bounded serial queue initially, with full-text and explicitly requested hover/expanded lookups ahead of speculative word prefetch. The current `selection_results()` yields the full sentence first, then processes unique words serially. A 200 ms lookup can still take several seconds to appear if it waits behind a paragraph's other words. Measure request-to-visible-result latency including this queue; per-word inference time alone is insufficient. Prioritization preserves the existing isolated-word input and compact/expanded outputs.

Cancel requests that have not been dispatched, and suppress completed results belonging to a superseded capture. Cancellation of a running calculation may let it finish without displaying its output; it should not routinely terminate the process and force another model load. Per-request deadlines, process failure recovery and shutdown remain necessary. A crash may reload the model and must be reported as recovery, separately from normal loaded latency. Model repair/removal requires releasing the affected backend and preparing it again; it must not leave an open model referring to replaced files.

The experimental runtime worker records actual CTranslate2 constructor calls, model paths, backend object IDs and process IDs before and during 100 simulated captures. It compares persistent Argos under the same protocol and records RAM, first use, median/p95 request latency and pending/stale cancellation behaviour. The portable native executable does not expose a model-construction counter. Its process lifetime, uncached request latency and upstream same-model loading guard provide supporting evidence, while direct native backend identity remains an instrumentation limitation. Neither prototype establishes that the existing application already has this lifecycle.

The user accepts best-effort meaning assessment. A candidate with slower preparation needs this resident production lifecycle and a useful quality/responsiveness tradeoff; loaded requests no longer have to be faster than Argos. Routine multi-second waits remain unacceptable. Preserve route/function decisions separately, Brazilian versus European Portuguese distinctions, known misleading alternatives and mechanically unhealthy baselines. Published scores and reference overlap do not certify all-language accuracy.

Package a chosen provider with versioned weights, tokenization and software/model licenses explicit. All runtime inference remains local. Validate the integrated resident lifecycle and request queue on this workstation. Another-PC testing has been waived by the user; the measured times describe this workstation rather than a universal hardware guarantee.

The completed local campaign measured 41 resident routes, each with 100 simulated captures and three fresh process/model preparations. The combined worker RSS after 100 captures is shown below. It includes the comparison Argos worker, the candidate and any separate pivot worker; hybrid packages can be duplicated. Treat these as prototype costs, not optimized packaged-application estimates.

| Prototype provider | Routes | Combined worker RSS after 100 captures | Candidate/Argos preparation ratio |
| --- | ---: | ---: | ---: |
| SMaLL-100 words with Argos full text | 31 | 711–835 MiB | 1.02–1.26× |
| OPUS West Germanic full text with Argos words | 1 | 635 MiB | 0.81× |

All 41 passed the earlier registered loaded-speed and prototype loading conditions. This historical runtime result is separate from the current best-effort semantic selections. Native preparation includes cache-verification probes, and fresh process starts share the OS file cache. Word runtime cycles time four cases per surface; broader/application stages cover both word surfaces on every registered case. A separate ten-capture German→Dutch supplement interleaves retained Argos compact/expanded words with its full-text provider and confirms stable loaded backend identities. The priority Portuguese follow-up adds a 100-capture mixed full-text/Argos-word workload and three fresh preparations.
